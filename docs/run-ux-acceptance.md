# Run UX acceptance: completion summary and isolated case folders

Status: bounded acceptance design and proof harness only. This document does not
claim the completion module, unique-child launcher routing, CI wiring, or owner
live validation is implemented. Parent integration must wire the harness to the
exact run handoffs and the completion presentation test double.

## Scope and proof boundary

This acceptance slice covers only two operator-facing behaviors:

1. A final end-of-run summary is honest about completed, partial, and failed
   collection, names each stage's status/skip reason, and points to the actual
   case and report paths.
2. Each default Collect run owns one unique child case folder under the existing
   C: root. A later run must not replace files from an earlier run.

The Windows proof is `tests/live/Invoke-WpdRunUxProof.ps1`. It is a verifier, not
an implementation or a collector. It takes the first and second exact case paths
as inputs. It never searches for the newest directory, runs collection, opens a
browser, deletes evidence, or modifies host policy. It refuses to run as a live
proof on non-Windows. Linux tests exercise only its pure name/status helpers and
PowerShell parsing.

The acceptance harness owns two small input formats; neither is an API
assumption about `Wpd.Completion.psm1` or the launchers:

- First-case baseline receipt: capture immediately after the first launcher
  completes and before the second launcher starts. The receipt stores the
  first-case file names, lengths, and SHA-256 values, including its run log. The
  receipt path must be outside `RootDirectory`, and an existing receipt is not
  overwritten.
- Summary envelope: supplied as `-SummaryEnvelopePath` or `-SummaryEnvelope`.
  It must contain `status` (`completed`, `partial`, or `failed`), integer
  `exitCode`, actual `caseDirectory`, `manifestPath`, and `reportPath`, arrays
  `errors` and `missingJson`, per-stage `stages` (`name`, `status`, and a
  non-empty `reason` for skipped stages), and `renderedText` containing the
  status and exact actual case/report paths. This is a test adapter contract,
  not a claim about the production completion module's receipt shape.
- Presentation argv receipt: generated by the Windows injected-runner test
  double at runner entry. It contains `runnerInjected: true`, `guiOpened: false`,
  `presentationStatus: accepted`, `runnerExitCode: 0`, the exact `caseDirectory`
  and `reportPath`, and an `argv` string array with those exact paths as
  separate arguments. A successful receipt proves argument delivery to the test
  double; it does not prove a browser was visible.

The current harness recognizes a case leaf of
`yyyyMMddTHHmmss[.fraction]Z-<8+ alphanumeric/hyphen run-id>` and can be aligned
by the parent if the chosen production timestamp/run-id spelling differs. The
parent must supply exact run paths from each launch's own output/receipt; it
must not infer paths by sorting the shared root or using a global latest-case
pointer.

## Compatibility and consent criteria

Positive requirements:

- On Windows, the default root remains `C:\WPD-Case`. Only default Collect
  output gains a fresh immediate child named from UTC time plus a random
  run-id. The C: root must not move under the repository, user profile, temp, or
  another drive.
- A caller-supplied collector `-OutputDirectory` is an explicit case path and
  remains exactly that path; it is not silently converted into a parent root or
  given another child. Existing direct collector callers retain that behavior.
- The existing `Run-Diagnostics.bat` and `START-HERE.bat` entry points must
  remain real tested paths. Their default collection mode routes to unique
  case children; `START-HERE.bat 2` must not fall back to the shared root.
- Plan remains non-collecting: it may write `diagnostic-plan.json` at its
  requested/default plan location, but it does not reserve or create a unique
  Collect child. Selecting consent-gated Tier 3 work requires
  `-ConfirmEscalationCollection` as the current entrypoint does, but Plan still
  describes the selection only; no Search or minifilter provider runs in Plan.
- Collect without `-ConfirmLocalCollection` refuses before making a new case
  directory. Selecting Search/minifilter collection additionally requires
  `-ConfirmEscalationCollection`; refusal leaves no new case directory or
  partial run output. Existing consent-gated WPR, Defender, minidump, boot-log,
  and remote options keep their independent consent checks.
- Verify remains read-only. It reads a named existing case, checks the
  production manifest/artifact/package integrity, and creates, removes, or
  rewrites no case files. The proof harness snapshots both folders before and
  after calling production Verify and fails if either changes.

These points match current entrypoint behavior in
`src/Invoke-WindowsPerformanceDiagnostics.ps1`: Plan writes the plan document,
Collect checks consent before creating its output directory, and Verify dispatches
to the read-only case verifier. Tier 3 Search/minifilter selection has an
independent escalation-consent gate. Parent integration must preserve those
ordering guarantees while changing only default Collect routing.

## Positive Windows acceptance criteria

Run the full launcher proof on each existing Windows CI OS (`windows-2022` and
`windows-2025`) and with both Windows PowerShell 5.1 and `pwsh`:

1. Invoke `Run-Diagnostics.bat` through `cmd.exe` as one run, with no explicit
   output override. Capture that invocation's exact case path and run-owned log
   path. Verify they are direct children/files of the first unique case, and
   capture a baseline receipt before starting another run.
2. Invoke `START-HERE.bat 2` through a separate `cmd.exe` invocation. Capture
   its exact case path and run-owned log from that invocation, not from a global
   directory scan. It must be a distinct immediate child of `C:\WPD-Case` with
   the UTC timestamp/run-id leaf form.
3. Prove the first case's complete file inventory and hashes are unchanged after
   the second run. If supplied, also compare the optional sentinel file against
   `ExpectedSentinelSha256`.
4. For both runs require a parseable final `diagnostic-manifest.json`, non-empty
   `report.html`, `escalation/search-service-context.json`,
   `escalation/minifilter-enumeration.json`, and the run-owned diagnostics log.
   Recompute manifest SHA-256 and size for report/Search/minifilter artifacts;
   require Search and minifilter records to be registered in the manifest's
   `evidenceIndex`. Preserve the real Search snapshot's `partial` status; the
   missing index-status provider is not an index-health claim. Minifilter proof
   must contain successful non-empty real filter evidence.
5. Supply a real summary envelope from the completion path for the second run.
   It must show `partial` for the current Search partial result, exit code zero,
   stage statuses (including explicit skip reasons), and the actual second
   case, manifest, and report paths in both fields and rendered text. Any errors
   or omitted optional JSON must remain visible as
   partial/failed rather than completed; required final evidence must still be
   present and pass its independent hash checks. The proof harness itself does
   not synthesize collection data or a summary.
6. Supply the injected-runner argv receipt proving that the final second-case
   and report paths reached the test runner as discrete Windows arguments.
   `guiOpened` must be false; CI makes no claim about hosted GUI visibility.
7. Run the production collector's `-Mode Verify -InputDirectory <exact case>`
   for each case under the current engine. Both manifest and package must report
   verified, and file snapshots before/after Verify must be identical.

No live collection is simulated on Linux. The owned focused tests parse the
PowerShell harness and exercise only the case-leaf and summary-envelope helper
logic.

## Negative acceptance criteria

The proof must fail closed for each of these cases; none may be reported as a
successful completed run:

- A missing/invalid manifest, report, Search JSON, minifilter JSON, or
  run-owned log; empty report; invalid required JSON; absent/duplicate artifact
  hash registration; mismatched SHA-256/size; or missing evidence-index record.
- A same-path first/second run, a path that is not an immediate child of the
  root, a leaf without a valid UTC timestamp and random run-id, or a reparse
  point in the case path/content.
- Any first-case file added, removed, or changed after the baseline (including
  report, log, sentinel, or evidence). A provided sentinel whose hash differs
  from its expected baseline also fails.
- Summary missing from proof inputs; malformed JSON; wrong actual case/report
  path; missing stage list or skip reason; unknown status; or rendered text that
  omits actual paths.
- A summary claiming `completed` with nonzero exit code, errors, missing JSON,
  a failed/partial stage, or partial Search evidence. The current Search
  service-only snapshot is partial, so a clean `completed` headline is false.
  A production Verify nonzero exit, malformed JSON, or non-verified package
  fails the proof.
- A failed presentation/runner status, nonzero runner exit, argv that omits or
  substitutes either final path, or any CI assertion that claims a browser was
  visibly opened.

Tamper behavior is checked through the production Verify path: an intact case
must verify, while an independently tampered artifact/package must be rejected
by Verify. The UX harness never tampers with a case during its positive run; a
separate negative fixture/CI leg must do the tamper and restore only its own
fixture data.

## Privacy and owner-live boundary

Every case folder and package is sensitive. Reports may include host, process,
service, event-log, crash, trace, and storage details. A unique folder is
isolation, not encryption, redaction, or safe-to-share packaging. Do not upload
case contents as ordinary workflow artifacts. If CI needs proof retention,
retain only a minimized harness receipt/summary and explicit non-sensitive
metadata; keep full collection output ephemeral or under the repository's
existing restricted live-proof policy.

Owner-live validation is still pending for UAC/elevation handoff and the final
browser-opening experience. Hosted GitHub runners can validate launcher
routing, exact paths, summary status, production Verify, and injected-runner
Windows argv, but they cannot establish that an interactive owner's UAC prompt
or browser is visible and usable. Owner validation must be a separate,
consented Windows client check; do not install software, reboot, suspend, or
change host policy as part of this acceptance harness.
